# TangentAtlas.LedgerService

The AtlasLedger server behind Tangent Atlas, and its client, schema, and tests. The ledger is generated by
[Bellerophon](https://github.com/bellerophon-dotnet/bellerophon) from the model in
`src/AtlasLedger.Server/bellerophon.json`; Bellerophon comes from nuget.org as packages, so this repository holds only
the product: the model, the hand-written server code, and its configuration.

Architecture, roadmap, decisions, and the deployment runbook are in `TangentAtlas.Platform/Documents`.

## Layout

| Path | Purpose |
|---|---|
| `src/AtlasLedger.Server` | The server (Bellerophon's Primary role) and owner of the model, `bellerophon.json`. The generated API over the in-memory ledger, write-behind persistence to SQL Server, recovery at startup, the NRules compliance engine, a simulated market feed. Its `Dockerfile` builds the container image. |
| `src/AtlasLedger.Client` | The client (Replica role), generated from the server's model: tenants, JSON script load and export, alerts, a local copy of a tenant, and an end-to-end walkthrough that doubles as a smoke test. `Data/firm-a.json` is the test organization. |
| `src/AtlasLedger.Schema` | The Entity Framework model of the database (Schema role) and its migrations. Used to create and evolve the database only; the server reads and writes with Bellerophon's generated SQL. |
| `src/TangentAtlas` | The enums the model's datatypes name. |
| `tests/AtlasLedger.Tests` | End to end: the server and client in one process over HTTP, including recovery. |
| `tests/AtlasLedger.Persistence.Tests` | The generated SQL writer and loader against SQL Server: LocalDB on Windows, or the server named by `BELLEROPHON_SQL_SERVER`; skipped without one. |

## Bellerophon

Package versions are in `Directory.Packages.props`. The generator (`Bellerophon`) and its libraries are released together,
so they share one property, `BellerophonVersion`; change it to move to a new release. The build writes the generated code
to `obj/<configuration>/net10.0/generated/` in each project.

## Build, test, run

```
dotnet build
dotnet test
dotnet run --project src/AtlasLedger.Server          # Development environment; runs until Ctrl+C
dotnet run --project src/AtlasLedger.Client          # in a second terminal: the walkthrough
```

The server keeps its database in memory unless `ConnectionStrings:Ledger` is set. To use a SQL Server database, apply the
migrations first (`LEDGER_SCHEMA_CONNECTION` names the database; LocalDB's `AtlasLedger` database otherwise):

```
dotnet tool restore
dotnet ef database update --project src/AtlasLedger.Schema
```

The server refuses to start outside the Development environment until bearer-token authentication is wired in.

## Services: on while you work, off otherwise

The base system (the API, persistence, and recovery) always runs.  The services on top of it, the market feed and
compliance, run only while switched on, and every switch starts off, so an idle server does no work and its database
can pause.  A service turned on stays on for four hours unless told otherwise (at most 24), then turns itself off.

```
dotnet run --project src/AtlasLedger.Client -- services                  # which are on, and until when
dotnet run --project src/AtlasLedger.Client -- services on               # all, for four hours
dotnet run --project src/AtlasLedger.Client -- services on compliance --for 1.5
dotnet run --project src/AtlasLedger.Client -- services off              # all
```

Set `ATLAS_LEDGER_SERVER` (or pass `--server`) to reach the server in Azure.  The walkthrough turns on what it needs and
turns it off again when it finishes.  The API is `v1/system/services`, the one route outside a tenant: only an allowed
tool acting as itself may use it, and anyone else signed in gets 404.
